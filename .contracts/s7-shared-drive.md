# s7-shared-drive — папка рекламы на общем диске

## Пути

Правятся:

    lib/ingest/drive-source.ts           два адреса запроса к Диску
    __tests__/ingest/drive-source.test.ts  дописываются проверки, утверждения не меняются
    breaks/s3-drive.ts                   если списка сломов у S3 нет — новый список
    README.md                            строка про общие диски

Не открываются: всё прочее. Кусок маленький и трогает ровно то, что названо.

## Задача

Отложенная задача S3, записанная в теле pull request дословно:

> **Папка на общем диске не читается.** Список запрашивается без `supportsAllDrives` и
> `includeItemsFromAllDrives`. Если папку перенесут, список вернётся пустым, и спасёт только
> наш отказ «ноль файлов `.csv`». Средство — два параметра в запросе.

Из всех отложенных задач проекта эта единственная, которая выстрелит **не у нас, а у того,
кто принимает работу**: папку `ads-exports` мы не создавали и не переносим, а лежать она может
где угодно. У нас она сегодня на личном диске служебного аккаунта и читается; у проверяющего
может оказаться на общем — и тогда загрузка рекламы вернёт ноль файлов.

Отказ на ноль `.csv` при этом сработает и скажет «в папке нет ни одного файла выгрузки», то
есть человек получит не тихую пустоту, а неверную причину: файлы в папке есть, их не видит
запрос. Неверная причина хуже отсутствия причины — по ней чинят не то.

## Что говорит документация

Три места, все из справочника Google Drive API v3.

**`supportsAllDrives`** — «Whether the requesting application supports both My Drives and shared
drives». Применяется и к `files.list`, и к `files.get`; в руководстве про общие диски сказано
прямо: без него «shared drive items, including both shared drives and files within a shared
drive, aren't returned».

**`includeItemsFromAllDrives`** — «Whether both My Drive and shared drive items should be
included in results». Только у `files.list`.

**`corpora`** — «Specifies a collection of items (files or documents) to which the query
applies. Supported items include: user, domain, drive, allDrives. Prefer user or drive to
allDrives for efficiency. **By default, corpora is set to `user`**».

## Отступление от буквы отложенной задачи, названное вслух

**Параметров не два, а три, и стоят они в двух разных адресах.**

Задача S3 говорила «средство — два параметра в запросе», подразумевая один запрос — список
папки. Этого мало: скачивание файла идёт вторым адресом, `files.get` с `alt=media`, и ему
нужен свой `supportsAllDrives`. Без него список вернётся полным, а скачивание каждого файла
откажет — то есть беда сдвинется на шаг и станет менее понятной, а не исчезнет.

Итого:

| Адрес | Что добавляется |
|---|---|
| `files.list` — список папки | `supportsAllDrives=true`, `includeItemsFromAllDrives=true`, `corpora=allDrives` |
| `files.get` с `alt=media` — содержимое файла | `supportsAllDrives=true` |

## Допущение, помеченное как допущение

**Справочник не говорит, достаточно ли двух флагов при `corpora` по умолчанию.** Описания
параметров независимы, и взаимодействие именно этой пары со значением `user` в документации
не описано. Проверить это у себя мы не можем: общего диска у нас нет.

Поэтому `corpora` задаётся явно значением `allDrives`, а не оставляется на умолчание. Это
единственное значение, которое по документации покрывает и личный диск, и общий, не требуя
знать идентификатор общего диска — а мы знаем только идентификатор папки. Замечание
документации «prefer user or drive to allDrives for efficiency» относится к скорости, а не к
верности, и на запросе одной папки по её идентификатору цены не имеет.

Отвергнутый вариант назван, чтобы решение можно было пересмотреть: можно было бы сперва
спросить `files.get` о самой папке с полем `driveId`, узнать общий диск и задать
`corpora=drive&driveId=…`. Это точнее и быстрее, но добавляет запрос и ветку «папка на личном
диске / папка на общем», то есть два пути вместо одного там, где второй путь нам нечем
проверить.

## Чем это закрыто

**Проверками на состав адреса.** Оба адреса строятся нашими чистыми функциями, и проверка
утверждает, какие параметры в них стоят. Это наблюдение за тем, что мы отправляем, а не за
тем, что ответит Google.

**Слом на каждый параметр.** Снятие любого из трёх у списка и одного у скачивания обязано
покрасить свою проверку.

## Названо вслух: чего этим не доказано

**Поведение Google на общем диске мы не наблюдали и наблюдать не можем** — общего диска у нас
нет. Доказано ровно одно: запрос уходит с теми параметрами, которые документация называет
необходимыми. Что Google на них ответит на настоящем общем диске, проверит тот, у кого такой
диск есть.

Это слабее, чем принято в проекте, и слабость названа, а не спрятана. Заменить её живой
проверкой можно только одним способом — завести общий диск, положить туда папку и прогнать
живой набор; если владелец сочтёт нужным, это отдельная задача.

**Проверки S1–S5 остаются зелёными без единой правки.** Кусок меняет два адреса и дописывает
проверки; ни одно принятое утверждение не трогается.

## Приёмка куска

| Что показывается | Как доказано |
|---|---|
| Список папки уходит с тремя параметрами | проверка состава адреса, слом на каждый |
| Скачивание уходит с `supportsAllDrives` | проверка состава адреса, слом |
| Живая загрузка папки по-прежнему работает | `NORDIC_PET_DB_TARGET=local npm run ingest:ads`, 279 строк из четырёх файлов |
| Прежние проверки S3 зелены без правки | `npm test`, дифф без удалений в их файле |

## Чего в этом куске нет

Входа по паролю, публикации, ничего из S6. Ни одной правки в разборе, слое фактов, метриках и
на экране. Живой проверки на настоящем общем диске — её нечем поставить.

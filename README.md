# Nordic Pet — дашборд прибыли

Один экран, который показывает, сколько магазин заработал на самом деле за выбранный месяц.

Два источника данных: Google Таблица `Nordic Pet — operations` и папка `ads-exports` на Google
Диске. Данные идут по цепочке: источник → сырые таблицы → таблицы фактов → метрики → экран.
Ни один шаг не перепрыгивается.

## Как это устроено

| Слой | Что в нём |
|---|---|
| Сырые таблицы | Повторяют источник как есть, вместе с его кривизной |
| Таблицы фактов | Приведённые к порядку числа, на которых считается экран |
| Метрики | Слой, который считает показатели |
| Экран | Только показывает. Ничего не считает |

## Локальная база

Нужны PostgreSQL 15 и Supabase CLI. Docker не нужен.

```bash
createdb nordic_pet   # один раз
npm run db:reset      # пересоздать из миграций и посева
npm test              # проверки, включая проверки базы
```

`npm run db:reset` работает только с базой `nordic_pet` на локальном хосте и отказывается от
любого другого адреса: рядом на сервере живут чужие базы, а пересоздание сносит в базе всё.
Посев эта команда применяет дважды — тогда неповторяемый посев валит саму команду, а не только
проверку.

## Загрузка Google Таблицы

```bash
NORDIC_PET_DB_TARGET=local npm run ingest:sheets
```

Команда читает шесть листов Таблицы «Nordic Pet — operations» и кладёт их в сырые таблицы как
есть, ничего не исправляя. Запущенная дважды подряд, она не меняет ни строки: по каждой таблице
она печатает количество строк и время последнего изменения, и у двух прогонов они совпадают.

Переменная `NORDIC_PET_DB_TARGET` обязательна и принимает ровно два значения — `local` и
`production`. Среда называется словом, а не выводится из того, какие ключи оказались заполнены:
иначе однажды запись ушла бы не в ту базу, ничем себя не выдав. Первой строкой команда печатает,
куда собирается писать, — до того, как что-нибудь запишет. Переменную можно держать и в
`.env.local`, но в командах ниже она написана явно, чтобы цель была видна прямо в строке запуска.

| Переменная | Для чего | Где живёт |
|---|---|---|
| `NORDIC_PET_DB_TARGET` | `local` или `production` | `.env.local`, переменные Vercel |
| `GOOGLE_APPLICATION_CREDENTIALS` | путь к файлу ключа; **в переменных Vercel не заводится** | только `.env.local` |
| `GOOGLE_SERVICE_ACCOUNT_KEY` | тот же ключ, но целиком значением | `.env.local`, переменные Vercel |
| `GOOGLE_SHEETS_SPREADSHEET_ID` | какую Таблицу читать | `.env.local`, переменные Vercel |
| `SUPABASE_DB_URL` | адрес боевой базы вместе с паролём | только переменные Vercel |
| `SUPABASE_DB_CA` | корневой сертификат боевой базы, если он не публично доверенный | только переменные Vercel |

Ключ служебного аккаунта приходит одним из двух способов, и **значение старше пути**: если
задана `GOOGLE_SERVICE_ACCOUNT_KEY`, путь к файлу не смотрится вовсе. Так сделано потому, что
на Vercel файла ключа нет и указать его негде — без второго способа кнопка «Обновить данные» в
бою до Google не дошла бы. Путь к файлу остаётся ради местной работы, где файл лежит на диске.
Значение задают под конкретный боевой запуск, а путь легко остаётся в окружении машины
разработчика случайно, — поэтому старшинство именно такое. Негодное значение отказывает сразу и
называет переменную и недостающее поле, но ни куска содержимого: сообщение уезжает в журнал,
ключ — нет.

Служебный аккаунт имеет доступ «Просмотр», и у Google запрашивается область только на чтение.
Дашборд во внешние сервисы не пишет никогда.

Боевой адрес не отдаётся драйверу базы строкой: он разбирается на шесть полей — хост, порт,
пользователь, пароль, база, шифрование, — и они уходят драйверу поимённо, а строка запроса
выбрасывается. Что бы ни было написано в адресе про `sslmode`, оно не читается: соединение идёт
с шифрованием и с проверкой сертификата всегда. Если корневая боевой базы не из публично
доверенных, её кладут в `SUPABASE_DB_CA` — кодом это не правится.

**После живой загрузки в локальной базе лежат настоящие данные, а не посев.** Это и есть работа
команды. Обычный набор проверок опирается на демонстрационные строки, поэтому перед ним базу
возвращают на место:

```bash
npm run db:reset
```

## Загрузка папки с Google Диска

```bash
NORDIC_PET_DB_TARGET=local npm run ingest:ads
```

Команда читает **всю** папку `ads-exports` и кладёт строки её файлов в сырую таблицу `raw.ads`
как есть, ничего не исправляя. Запущенная дважды подряд, она не меняет ни строки: вывод двух
прогонов совпадает целиком, вместе со временем последнего изменения.

| Переменная | Для чего | Где живёт |
|---|---|---|
| `GOOGLE_DRIVE_ADS_FOLDER_ID` | какую папку читать | `.env.local`, переменные Vercel |

Папка читается по идентификатору, а не по имени: одинаковых имён на Диске может быть сколько
угодно. Служебный аккаунт имеет доступ «Просмотр», и у Google запрашивается область только на
чтение Диска — отдельная от области Таблиц, чтобы загрузчик Таблицы не получал прав на Диск.

**Папка может лежать и на общем диске, а не только на личном диске служебного аккаунта.**
Список файлов и содержимое каждого файла — два разных обращения, и поддержка общих дисков
нужна каждому своя. Без неё папка, перенесённая на общий диск, вернулась бы пустым списком, а
отказ «в папке нет ни одного файла .csv» назвал бы неверную причину: файлы там есть, их не
видит запрос. Область поиска при этом задана явно — «все диски», а не оставлена на умолчании,
которое ищет только по личному. Доказано это составом наших запросов, а не живой папкой на
общем диске: общего диска у нас нет, и поведения Google на нём никто не наблюдал.

**Папка грузится целиком и за один раз — по файлу нельзя.** Запись в базе подчищает всю папку:
всё, чего нет во входном снимке, из `raw.ads` удаляется. Вызов со строками одного файла стёр бы
строки остальных площадок, и запись была бы права — отличить снимок одного файла от снимка папки
ей нечем. Поэтому загрузчик читает все файлы, разбирает их все и только потом пишет, одним
вызовом.

Отсюда же строгость к неполноте. Загрузка отказывается целиком, если:

| Что случилось | Почему это отказ |
|---|---|
| Диск отдал неполный список папки | строки не попавших в список файлов были бы удалены |
| в папке нет ни одного `.csv` | пустой снимок вычистил бы таблицу дочиста |
| файл `.csv` оказался Таблицей Google | скачать его содержимое нельзя, а пропустив, мы стёрли бы всю историю этой площадки |
| два файла с одинаковым именем | адрес строки — имя файла плюс номер строки, и они слились бы в один |
| размер или контрольная сумма скачанного не сошлись с теми, что назвал Диск | файл правили во время чтения или он испортился по дороге |
| в файле есть заголовок и ни одной строки данных | это след сбоя выгрузки: площадку без расхода просто не кладут в папку |

Каждый такой отказ называет файл и говорит, что сделать. Файлы, не похожие на выгрузку —
заметка, подпапка, ярлык, — не отказ: они пропускаются, а их имена команда называет в выводе.

**Дедупликации здесь нет.** В папке лежат две выгрузки `meta`, совпадающие посимвольно и
различающиеся только концом строки, и обе ложатся в базу целиком: сырой слой повторяет источник
как есть. Площадка из имени файла тоже не выводится. Выбрать лишнюю выгрузку и назвать площадку —
работа слоя фактов.

После живой загрузки базу так же возвращают на место командой `npm run db:reset`.

## Разбор сырых строк в слой фактов

```bash
NORDIC_PET_DB_TARGET=local npm run facts
```

Команда читает семь сырых таблиц и заполняет семь таблиц фактов: даты становятся датами,
деньги — числами с валютой в соседней колонке, артикул приводится к одному написанию,
у рекламы появляется площадка. В сеть она не ходит вовсе — ни в Google, ни куда-либо ещё.
Запущенная дважды подряд, она не меняет ни одной строки.

Слой фактов пересобирается **целиком** при каждом прогоне, а не по признаку «что изменилось
с прошлого раза». Отметка «до какого места разобрано» — это состояние, и у него есть гонка,
которая теряет строку молча и навсегда: загрузка, начавшаяся раньше разбора и зафиксированная
позже, оставит строку с отметкой меньше запомненной, и такая строка не попадёт ни в один
пересчёт. Полная пересборка шестисот строк стоит доли секунды и исполняет обязательство
контракта S1 по построению: изменившаяся сырая строка не может остаться неразобранной,
потому что разбирается каждая.

**Разбор ничего не угадывает.** Форм даты в источнике две — `ГГГГ-ММ-ДД` и `ДД.ММ.ГГГГ`, —
и обе понимаются; третья форма, несуществующая дата, непонятное число, лишние знаки после
запятой — отказ с указанием листа, строки, столбца, значения и того, что делать. Отказ
собирает все непонятые места разом, а не первое: лист правят один раз.

Пустая денежная ячейка — это `null`, «источник промолчал». Ноль вместо неё не пишется нигде:
отсутствующая цена поставщика имеет своё правило счёта, а превращённая в ноль она сделала бы
прибыль красивее ровно на ту сумму, которой мы не знаем. Сколько таких ячеек нашлось, команда
печатает числом по каждой таблице.

### Что останавливает разбор

| Что случилось | Почему это отказ |
|---|---|
| два курса на одну дату, две цены на артикул и дату, две ставки на способ оплаты | это свойства, а не суммы: соединение с задвоенной строкой удваивает деньги и выглядит правдоподобно |
| строки одного заказа разошлись способом оплаты или датой | заказ целиком принадлежит одному дню и одному способу оплаты, иначе врёт правило комиссии |
| после свёртки копий столкнулись площадка, день и кампания | две наполовину совпавшие выгрузки сложились бы как разные расходы |
| нет курса на день, за который есть расход рекламы | расход выпал бы из счёта, занизив рекламу и завысив прибыль |
| в заказах встретился способ оплаты, которого нет в ставках | комиссия по этим заказам вышла бы нулевой |

Отсутствующая цена поставщика в этот список **не** входит: у неё есть своё правило счёта и
своя строка на экране. Это названная неполнота, а не молчаливая.

Первые четыре случая закрыты не только кодом, но и уникальными ключами в самой базе —
отложенными до конца транзакции, потому что внутри одной записи строки законно меняются
местами. Код отказывает первым и человеческими словами; ключ стоит за ним и делает
молчаливую запись противоречия невозможной, а не нежелательной.

### Что называется, но не останавливает

Строки, совпавшие между собой **по всем колонкам источника** до последней, — почти наверняка
строка, скопированная руками: она удвоит и выручку, и штуки, и себестоимость, выглядя при
этом безупречно. Отказом это не делается — законный случай вообразить можно. Команда
сообщает числом, сколько таких строк нашлось в заказах и в возвратах, и перечисляет их
адреса. Ноль печатается тоже: «близнецов: 0» отличимо от отсутствия проверки.

Так же называются свёрнутые копии выгрузки и найденные площадки.

### Две выгрузки meta

В папке лежат два экземпляра выгрузки `meta`. Они сравнены по содержимому — построчно, по
разобранным значениям: 93 строки из 93 совпали, расход у обоих 2791,73 доллара, а различаются
файлы только концом строки. Это два экземпляра одной выгрузки, и в факты идёт один.

Копия опознаётся **по содержимому** и никогда по имени и никогда по времени правки на Диске:
время говорит о том, когда человек нажал кнопку, а не о том, какие деньги настоящие.
Площадка входит в сравниваемое содержимое — иначе два файла разных кабинетов со случайно
совпавшими числами оказались бы копиями, и свёртка стёрла бы расход целой площадки.
Какой из экземпляров остаётся, не меняет ни одного числа и выбирается ради повторяемости
адресов: короткое имя, при равной длине — первое по порядку кодовых знаков.

## Экран

```bash
npm run dev
```

Страница `/` показывает за выбранный месяц выручку, затраты, итог, таблицу товаров и честность
данных: долю чистой выручки, посчитанную по настоящей цене поставщика. Месяц берётся из адреса
(`?m=2026-03`); без него показан последний месяц, за который есть заказы. Список месяцев в
навигации — те, за которые есть хоть одна строка заказов, рекламы или расходов.

Экран не считает ничего — он печатает готовые строки, которые вернул слой метрик
(`lib/metrics/report.ts`). Округление, деньги в `numeric`, деление на ноль как «нет данных» —
всё это сделано в SQL и в самом отчёте; разметка (`app/page.tsx`) ни разу не складывает и не
делит два числа отчёта между собой.

Отдельным блоком экран печатает неполноту данных: по каждому виду пустой ячейки в источнике —
сколько их и по каким адресам. Ноль печатается тоже, чтобы отличить «дыр нет» от «эту дыру не
проверяли».

## Кнопка «Обновить данные»

Кнопка на экране перечитывает оба источника и пересобирает факты — три шага в жёстком порядке:
загрузка Таблицы → загрузка папки → разбор. Своей дороги в базу у неё нет: она зовёт те же три
работы, что и команды `ingest:sheets`, `ingest:ads` и `facts` из `lib/commands.ts`, — по имени,
через список, а не в обход него.

Между шагами есть щель, доставшаяся от того, что каждый шаг — своя собственная транзакция: если
источники перечитаны, а разбор отказал, сырьё частично новое, а факты — вчерашние. Кнопка
показывает это двумя вещами разом: читаемым текстом, на каком шаге остановились и что сделать, и
изменённым видом блока отчёта — числа гаснут и помечаются как устаревшие, а не остаются в прежнем
виде рядом с текстом отказа.

## Команда метрик

```bash
NORDIC_PET_DB_TARGET=local npm run metrics
```

Печатает отчёт месяца в терминал — те же семь правил счёта и те же поля, что показывает экран, и
теми же функциями формата (`lib/metrics/format.ts`), чтобы числа на экране и в выводе команды не
расходились. Нужна там, где нет ни экрана, ни браузера: боевой прогон против боевой базы читает
пять итогов приёмки (чистую выручку, себестоимость, рекламу, комиссии, прибыль) из этого вывода.

Месяц — необязательный первый довод командной строки, вида `ГГГГ-ММ`:

```bash
NORDIC_PET_DB_TARGET=local npm run metrics -- 2026-03
```

Без довода команда сама берёт последний месяц, за который есть заказы — то же правило, что у
экрана без адресной строки. Довод не в форме `ГГГГ-ММ` — отказ, называющий верную форму, а не
ошибка базы. В базу команда не пишет: снимок, который она читает, идёт той же транзакцией
`repeatable read read only`, что и у экрана и у кнопки.

## Вход

Дашборд закрыт паролем целиком. Устройство — **закрыто всё, кроме перечисленного списка
исключений**, а не «закрываем перечисленные пути». Разница вся в завтрашнем пути: перечень
закрываемого оставляет его открытым по забывчивости, перечень исключений — закрытым, пока
кто-то сознательно не впишет его в список.

| Адрес | Открыт ли без входа | Почему |
|---|---|---|
| `/health` | да | отдаёт только номер коммита — не экран и не данные |
| `/login` | да | не пуская сюда, войти нельзя вовсе |
| всё остальное | нет | включая страницу отчёта и серверное действие кнопки |

`/health` остаётся открытой потому, что её единственное дело — отличать «выложилось новое» от
«браузер показал старое», а за паролем она этого делать не сможет. Что она не отдаёт ничего
сверх номера коммита, сторожит своя проверка. Растущий список исключений — признак, что защиту
пора пересматривать, а не пополнять.

Слоёв закрытия два, и второй не перестраховка. Первый закрывает всё, о чём никто не подумал.
Второй — свой сторож у каждого пути, который отдаёт числа или делает работу; этого требует
документация Next: «Always verify authentication and authorization inside each Server Function
rather than relying on Proxy alone». Перенос серверного действия на другой путь или правка
образца молча вывели бы его из-под первого слоя, а второй остался бы на месте.

Вход выдаёт cookie, подписанную HMAC-SHA256 секретом из переменной окружения. В cookie нет
ничего, кроме срока годности: ни логина, ни пароля, ни признака прав — вход в дашборде один на
всех, и возить в ней нечего. Чего в ней нет, то не утечёт.

Срок жизни — **двенадцать часов**. Дашборд смотрят рабочими подходами, а не держат открытым
неделями: двенадцать часов покрывают рабочий день с запасом и не переживают ночь. Меньше —
человек будет входить посреди работы; больше — забытая вкладка на чужой машине остаётся входом
дольше суток.

Cookie не связана ни с логином, ни с паролем, и отсюда следствие, которое стоит знать заранее:
смена пароля уже выданные cookie не отзывает — они пускают до конца своих двенадцати часов.
Отозвать их разом можно только сменой секрета подписи.

Неверный вход отвечает одинаково на любой ввод: ни «такого логина нет», ни «пароль не подошёл».
Разные ответы говорят подбирающему, какая половина уже угадана, и превращают перебор двух
неизвестных в перебор одного.

| Переменная | Для чего | Где живёт |
|---|---|---|
| `NORDIC_PET_LOGIN` | логин | переменные Vercel, `.env.local` |
| `NORDIC_PET_PASSWORD` | пароль | переменные Vercel, `.env.local` |
| `NORDIC_PET_SESSION_SECRET` | секрет подписи cookie | переменные Vercel, `.env.local` |

Значения придумывает и кладёт владелец. В код, в репозиторий и в переписку они не попадают
никогда; в `.env.local` для местной работы лежат заведомо ненастоящие. Секрет подписи —
случайная строка не короче 32 байт, например из `openssl rand -base64 32`.

## Публикация

Приложение живёт на Vercel: ветка сливается в `main`, Vercel собирает и выкладывает.

| Переменная | Что в ней |
|---|---|
| `NORDIC_PET_LOGIN` | логин входа |
| `NORDIC_PET_PASSWORD` | пароль входа |
| `NORDIC_PET_SESSION_SECRET` | секрет подписи cookie, не короче 32 байт |
| `NORDIC_PET_DB_TARGET` | `production` |
| `SUPABASE_DB_URL` | адрес боевой базы вместе с паролём |
| `SUPABASE_DB_CA` | корневой сертификат боевой базы, если он не публично доверенный |
| `GOOGLE_SERVICE_ACCOUNT_KEY` | ключ служебного аккаунта целиком, одной строкой |
| `GOOGLE_SHEETS_SPREADSHEET_ID` | какую Таблицу читать |
| `GOOGLE_DRIVE_ADS_FOLDER_ID` | какую папку читать |

`GOOGLE_APPLICATION_CREDENTIALS` в переменных Vercel не заводится: файла ключа там нет и
положить его некуда. Поэтому в бою ключ приходит значением, а путь остаётся для местной работы.

Что делает руками владелец и почему не мы:

| Шаг | Почему |
|---|---|
| Придумать логин, пароль и секрет подписи и вписать их в переменные проекта | секретов у нас нет и быть не должно: придуманный нами секрет прошёл бы через переписку |
| Проверить, что переменные заведены во всех средах, где приложение собирается | доступа к панели хостинга у нас нет |
| Заменить служебный ключ Supabase, если он где-то показывался | ротация ключей — решение владельца |

## Проверки

Проверок два набора, и делятся они по тому, нужна ли им сеть.

| Команда | Что проверяет | Идёт в `ci` |
|---|---|---|
| `npm test` | всё, что не ходит наружу, включая разбор на настоящей базе | да |
| `NORDIC_PET_DB_TARGET=local NORDIC_PET_LIVE_URL=<адрес> npm run test:live` | весь живой набор: поход в Google, настоящую запись и закрытие дашборда снаружи | нет |
| `NORDIC_PET_LIVE_URL=<адрес> npm run test:live -- __tests__/live/access.live.ts` | только закрытие дашборда снаружи | нет |

Живому набору **целиком** нужны обе переменные: без адреса выложенного дашборда проверка
закрытия краснеет нарочно, и команда, запущенная с одной переменной, вернёт ненулевой код —
не потому, что сломан поход в Google.

Живой набор в `ci` не идёт: ни ключей служебного аккаунта, ни адреса выложенного дашборда там
нет и не будет. Он не «пропускается при отсутствии среды» — без неё он краснеет, а вынесен
отдельно именем файла: `*.live.ts` не подходит под образец обычного набора вовсе. Проверка,
которая молча исчезает вместе со средой, создаёт видимость проверенного там, где не проверено
ничего.

Живых проверок четыре. Три из них ходят в Google и пишут в базу по-настоящему; они возвращают
базу такой, какой её нашли — посев применяется заново тем же файлом, которым пересоздаётся база,
поэтому `npm test` после них остаётся зелёным. Идут они по очереди, а не вперемешку: запущенные
разом, они затирали бы работу друг друга одним и тем же посевом.

Четвёртая — проверка закрытия снаружи — в базу не ходит вовсе: она стучится по настоящему адресу
дашборда и смотрит, что видно без входа. Ей нужен адрес в `NORDIC_PET_LIVE_URL`, и без него она
**краснеет**, называя переменную, а не пропускается: проверка, исчезающая вместе со средой,
создаёт видимость проверенного там, где не проверено ничего.

# S6 — вход по паролю, закрытие всех путей, публикация и приёмка снаружи

> **Исполнителю:** план исполняется задача за задачей; между задачами — проверка кода тем,
> у кого нет контекста автора. Шаги помечены `- [ ]` для отметки.

**Цель:** дашборд живёт по адресу в интернете и закрыт паролем; человек без пароля не видит
ни экрана, ни чисел — ни страницей, ни серверным действием кнопки; кнопка в бою по-настоящему
доходит до Google и до боевой базы.

**Устройство:** два независимых слоя. Первый — `proxy.ts`: закрыто всё, кроме короткого
названного списка исключений, — он ловит завтрашний путь, которого ещё нет. Второй — свой
сторож у каждого пути, который отдаёт числа или делает работу; так требует и владелец, и
документация Next: «Always verify authentication and authorization inside each Server Function
rather than relying on Proxy alone» (nextjs.org/docs/app/api-reference/file-conventions/proxy,
раздел «Execution order»). Cookie подписана HMAC-SHA256 секретом из переменной окружения,
живёт двенадцать часов, тела не несёт.

**Чем пользуемся:** Next.js 16.3.3 (`proxy.ts`, `cookies()` из `next/headers`), `node:crypto`
(`createHmac`, `timingSafeEqual`), vitest 4, `google-auth-library` 11.

**Контракт:** `.contracts/s6-access.md` на ветке `contract/s6-access` (принят владельцем),
плюс три поправки владельца от 3 сентября 2026 года — они в разделе «Поправки» ниже.

## Общие ограничения

- Ветка `feat/s6-access` от `main` (`cfcc2f6`). В `main` не писать.
- **В принятых проверках S1–S5 правится только обвязка трёх названных файлов** (разрешение
  владельца от 3 сентября, условия — в разделе «Развилка»). Все прочие файлы проверок прошлых
  кусков не открываются вовсе; дописывать рядом — можно. Доказывается
  `git diff --numstat main..HEAD -- __tests__/`: у всех файлов, кроме трёх названных, нули.
- Не открываются: `lib/facts/**`, `lib/metrics/**`, `lib/ingest/**` кроме
  `lib/ingest/google-access.ts`, `supabase/migrations/**`, `supabase/seed.sql`,
  `vitest.config.ts`, `.github/workflows/ci.yml`.
- Логин, пароль и секрет подписи придумывает владелец и кладёт в Vercel. В коде, в git и в
  переписке их нет. Для местных проверок — заведомо ненастоящие значения вида
  `не-настоящий-пароль-для-проверок`.
- Ворота проверяются кодом возврата своей команды, не через конвейер: команда отдельной
  строкой, `$?` в переменную, вывод при нужде — в файл.
- Срок жизни cookie — **двенадцать часов**, число названо в контракте с доводом.
- Список исключений — ровно `/health`. Каждая строка исключения и каждое отступление от
  контракта уходят в тело pull request отдельной строкой с доводом.
- Секрет подписи: HMAC-SHA256, `node:crypto`. Библиотеки `jose` не добавляем — см.
  отступление 3.

## Развилка: решена владельцем — вариант Б

**Что нашлось на разведке.** Три принятые проверки S5 зовут защищаемые пути **напрямую, без
запроса Next**:

| Файл проверки | Что зовёт | Прежний слом S5, которым доказывается уцелевшее утверждение |
|---|---|---|
| `__tests__/metrics/screen-month.test.tsx` | `HomePage({ searchParams })` — трижды | `month-param-ignored`, `nav-links-drop-month`, `bad-month-crashes-page` |
| `__tests__/metrics/refresh.test.tsx` | `refreshAction()` по-настоящему и `HomePage(...)` | `action-extra-fetch`, `button-not-on-screen` |
| `__tests__/metrics/refresh-action.test.ts` | `refreshAction()` — четырежды | `no-revalidate-after-refresh` |

А `cookies()` вне запроса Next не возвращает пустоту, а отказывает. Проверено запуском:

```
node --input-type=module -e "import('next/dist/server/request/cookies.js')…"
→ THREW: Error | `cookies` was called outside a request scope.
```

**Решение владельца — вариант Б: правятся три принятые проверки, сторож остаётся без
исключений.** Его довод, дословно: «Защита не имеет права содержать ветку „пропустить“,
которая включается по значению переменной среды. Сегодня она недостижима в бою, а завтра
кто-то соберёт приложение с другой средой, и единственное, что стоит между посторонним и
деньгами, окажется настройкой окружения». Отсюда правило устройства сторожа: **нет запроса —
нет доступа**, и никакого различения сред внутри защиты.

**Три условия владельца к правке принятых проверок** (исполняются в задаче 4б):

1. Меняется только обвязка, которой проверка готовит вызов. Ни одно ожидание не
   переписывается и не удаляется.
2. На каждую из трёх показывается, что её собственный прежний слом по-прежнему красит
   именно её: сломал — красная, вернул — зелёная. Прогон прежних сломов S5 по именам из
   таблицы выше, вердикт обязан быть «своё».
3. В теле pull request — отдельный раздел: какие три проверки тронуты, почему, и вывод
   сравнения с числом изменённых и удалённых строк по каждой.

## Отступления от буквы контракта

**Отступление 1 — файл называется `proxy.ts`, а не `middleware.ts`.** Контракт называет
`middleware.ts`; в Next 16 это имя объявлено устаревшим самой библиотекой. Сборка печатает:
`The "middleware" file convention is deprecated. Please use "proxy" instead`
(`node_modules/next/dist/build/index.js:730`), документация подтверждает: «The `middleware`
file convention is deprecated and has been renamed to `proxy`»
(nextjs.org/docs/app/api-reference/file-conventions/proxy). Устройство и обязательства —
ровно те, что в контракте; меняется имя файла и имя вызываемой функции. Заодно это снимает
вопрос среды исполнения: «Proxy defaults to using the Node.js runtime» (там же), значит
`node:crypto` доступен, и проверка подписи в первом слое идёт тем же кодом, что и во втором.

**Отступление 2 — в исключениях, кроме `/health`, стоят сборочные файлы Next.** Образец
`proxy.ts` не покрывает `/_next/static`, `/_next/image` и `/favicon.ico`. Довод: это файлы
сборки, одинаковые для всех посетителей, чисел отчёта в них нет и быть не может (страница
отчёта помечена `force-dynamic` и заранее не отрисовывается), а закрытые они ломают саму
страницу входа — ей нечем нарисоваться. Так же поступает и пример в документации Next
(«Negative matching»). Строка исключений владельца остаётся одна — `/health`; сборочные
файлы стоят в образце `matcher`, названы здесь и уйдут в тело PR отдельной строкой.

**Отступление 3 — подпись своя на `node:crypto`, а не библиотека.** Документация Next
советует `jose` или `iron-session`. Берём `node:crypto`: подписываем строку срока годности
HMAC-SHA256 и сверяем `timingSafeEqual`. Довод: в cookie нет ни одного поля, кроме срока
годности, — JWT здесь возит формат ради формата, а новая зависимость в защите стоит дороже
двадцати строк на стандартном модуле. Приём — тот же, что описан в документации Next
(«Generating a secret key» → `SESSION_SECRET` в переменной окружения).

**Отступление 4 — ключ Google берётся через `GoogleAuth({ credentials })`, а не через
`new JWT(...)`.** Контракт показывает пример README библиотеки с классом `JWT`. Берём тот же
приём в форме, которую библиотека объявляет в своих типах:
`credentials?: JWTInput` в `GoogleAuthOptions` (`googleauth.d.ts:131`). Довод: `googleAuth()`
возвращает `GoogleAuth` и сегодня, значит тип возврата не меняется, и принятая проверка S2
`__tests__/ingest/google-access.test.ts`, читающая поле `scopes`, остаётся нетронутой. Само
разрешение брать ключ значением — из README библиотеки: «Instead of loading credentials from
a key file, you can also provide them using an environment variable».

дают строку cookie, секрет и «сейчас», и он отвечает да/нет. Поэтому его проверки не требуют
ни запроса Next, ни подставок времени. Всё, что знает про `next/headers`, заперто в
`guard.ts` — там же и живёт развилка «нет запроса».

**Договор наружу:**

```ts
// lib/auth/session.ts
export const SESSION_COOKIE = 'nordic_pet_session'
export const SESSION_HOURS = 12
export type Состояние = 'годна' | 'нет cookie' | 'подпись чужая' | 'просрочена' | 'нет секрета'
```

## Задача 2 — страница входа и серверное действие

**Файлы:** создать `lib/auth/login.ts`, `app/login/page.tsx`, `app/login/action.ts`,
`__tests__/auth/login.test.ts`.

**Договор наружу:**

```ts
// lib/auth/login.ts
export type ИсходВхода = { ok: true } | { ok: false; text: string }
export type ХранилищеCookie = { set: (имя: string, значение: string, настройки: Record<string, unknown>) => void }
export type ЗависимостиВхода = { env: Record<string,string|undefined>; now: number; cookies: ХранилищеCookie }
export async function войти(логин: string, пароль: string, deps: ЗависимостиВхода): Promise<ИсходВхода>
```

`app/login/action.ts` — тонкая обёртка `'use server'`: достаёт два поля из `FormData`,
зовёт `войти()` с настоящим хранилищем `cookies()` из `next/headers`, при удаче зовёт
`redirect('/')`. Ни одного решения она сама не принимает — тем же приёмом, что
`app/refresh-action.ts` в S5.

- [ ] **Шаг 1. Проверки:**

```ts
function хранилище() {
  const записи: Array<{ имя: string; значение: string; настройки: Record<string, unknown> }> = []
  return { записи, set: (имя, значение, настройки) => { записи.push({ имя, значение, настройки }) } }
}
const СРЕДА = {
  NORDIC_PET_LOGIN: 'не-настоящий-логин',
  NORDIC_PET_PASSWORD: 'не-настоящий-пароль',
  NORDIC_PET_SESSION_SECRET: 'не-настоящий-секрет-подписи-для-проверок-0123456789',
}

test('cookie выдаётся с HttpOnly, Secure и SameSite', async () => {
  const c = хранилище()
  expect(await войти('не-настоящий-логин', 'не-настоящий-пароль', { env: СРЕДА, now: СЕЙЧАС, cookies: c })).toEqual({ ok: true })
  expect(c.записи).toHaveLength(1)
  const { имя, настройки } = c.записи[0]
  expect(имя).toBe(SESSION_COOKIE)
  expect(настройки).toMatchObject({ httpOnly: true, secure: true, sameSite: 'lax', path: '/' })
  expect((настройки.expires as Date).getTime() - СЕЙЧАС).toBe(12 * 60 * 60 * 1000)
})

test('неверный вход отвечает одинаково на любой ввод', async () => {
  const исходы = []
  for (const [л, п] of [['чужой', 'не-настоящий-пароль'], ['не-настоящий-логин', 'чужой'], ['чужой', 'чужой'], ['', '']]) {
    const c = хранилище()
    исходы.push(await войти(л, п, { env: СРЕДА, now: СЕЙЧАС, cookies: c }))
    expect(c.записи, 'неверный вход cookie не выдаёт').toEqual([])
  }
  expect(new Set(исходы.map((и) => JSON.stringify(и))).size, 'ответы обязаны совпасть до знака').toBe(1)
  expect(исходы[0]).toEqual({ ok: false, text: 'Логин или пароль не подошли' })
})

test('отказ входа не называет ни пароля, ни секрета', async () => {
  const c = хранилище()
  const исход = await войти('чужой', 'не-настоящий-пароль', { env: СРЕДА, now: СЕЙЧАС, cookies: c })
  const текст = JSON.stringify(исход)
  expect(текст).not.toContain(СРЕДА.NORDIC_PET_PASSWORD)
  expect(текст).not.toContain(СРЕДА.NORDIC_PET_SESSION_SECRET)
})

test('неназванные переменные входа — отказ, называющий, что сделать', async () => {
  const c = хранилище()
  const исход = await войти('кто-то', 'что-то', { env: {}, now: СЕЙЧАС, cookies: c })
  expect(исход).toMatchObject({ ok: false })
  expect((исход as { text: string }).text).toMatch(/NORDIC_PET_LOGIN/)
  expect((исход as { text: string }).text).toMatch(/Vercel/)
  expect(c.записи).toEqual([])
})
```

**Договор наружу:**

```ts
// lib/auth/guard.ts
export type Доступ = 'пускать' | 'отказать'

  читатьCookie?: () => Promise<string | undefined>,
  env?: Record<string, string | undefined>,
```

По умолчанию `читатьCookie` — настоящее чтение из `next/headers`. Вне запроса Next оно
отказывает; этот отказ узнаётся по тексту `cookies` was called outside a request scope и
означает «запроса нет вовсе». Ответ на него один и без условий: **отказать**. Ни среды, ни
признака сборки, ни какого-либо иного внешнего признака сторож не читает — разрешающих веток
в защите нет вовсе. Довод владельца — в разделе «Развилка».

Довод «нет запроса — отказ», а не «нет запроса — падение»: отказ определён и одинаков, а
необработанное падение отдало бы посетителю страницу ошибки хостинга, по которой не понять,
закрыто тут или сломано.

## Куда смотреть первым делом

Если что-то в этом куске окажется не так, вероятнее всего это одно из трёх — в порядке
вероятности:

1. **Обвязка трёх правленых проверок S5.** Единственное место, где чужое принятое
   утверждение проверяется в изменённом окружении.
2. **Образец `matcher` в `proxy.ts`.** Опечатка в нём не краснеет ни одной проверкой
   вида «путь закрыт»: она молча выводит путь из-под первого слоя целиком. Второй слой
   такой путь всё равно закроет, но список исключений перестанет описывать правду.
3. **Ключ Google значением на боевой стороне.** Единственный шов, который проверками не
   доказать до конца: до Google на местной машине дело доходит поддельным ключом, а
   настоящий поход в бою случается ровно один раз — при нажатии кнопки.

## Пути, ни разу не виденные в настоящих данных

- Просроченная cookie в бою: двенадцать часов ещё ни разу не истекали.
- Отказ Google на боевом ключе значением: местный путь ходит файлом.
- Одновременный вход двух человек: cookie не несёт тела, конфликта быть не должно —
  но это рассуждение, а не наблюдение.

## Известные ловушки, которые выстрелят в следующем куске

- **S7 (папка на общем диске) добавит переменную и новый путь.** Новый путь окажется
  закрытым сам собой — так устроен `proxy.ts`, — и это верно; но если S7 заведёт свой
  адрес для проверки состояния, его придётся сознательно вписать в список исключений, и
  строка потребует довода в теле PR.
- **`vitest.live.config.ts` говорит «живых проверок две», а после этого куска их четыре.**
  Файл в запретном списке S6 — задача, упирающаяся в его правку, обязана остановиться.
  Записано, чтобы читающий не поверил пояснению.

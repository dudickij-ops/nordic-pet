# S2 — загрузка Google Таблицы в сырой слой. План работ

> **Для исполнителя:** план выполняется задача за задачей. Шаги отмечаются галочками (`- [ ]`).
> Каждая задача заканчивается коммитом и проверяемым результатом.

**Цель:** одна команда читает шесть листов Google Таблицы «Nordic Pet — operations» и кладёт их
в сырые таблицы, ничего не исправляя; запущенная дважды подряд, не меняет в базе ни строки, ни
байта, и это видно из вывода самой команды.

**Устройство:** загрузка — функция, команда — обёртка в семь строк; кнопка S5 позовёт ту же
функцию. Читается вся Таблица одним запросом, пишется шестью вызовами `raw.replace_*` в одной
транзакции. Путь к базе у загрузчика свой, и среда в нём названа словом, а не выведена из
косвенных признаков; замок S1 на разрушающую команду не тронут.

**Инструменты:** `google-auth-library` (официальный пакет Google), драйвер `pg`, vitest,
PostgreSQL 15 локально и в `ci`.

**Контракт:** `.contracts/s2-sheets.md` на ветке `contract/s2-sheets` (коммит `eb4a48e`).
План спорит с контрактом, а не заменяет его: исполнитель читает оба.

## Общие ограничения

- Работа `ci` не переименовывается и не делится надвое. Новых шагов в ней не появляется:
  `npm test` уже запускается, а живая проверка в `ci` не идёт.
- `lib/db-url.ts`, `scripts/db-reset.ts`, миграции и посев не меняются ни на строку. Если
  задача упирается в необходимость их поправить — это стоп-сигнал, а не повод править.
- В сырые таблицы пишут только функции `raw.replace_*`. Ни одной прямой вставки.
- Грязь источника не чинится: значения ячеек доезжают в базу посимвольно.
- У Google запрашивается область только на чтение. Кода записи в Google нет.
- Пароль боевой базы не появляется ни в выводе, ни в сообщении об ошибке, ни в журнале.
- Тесты пишутся до кода и сперва краснеют. Красное показывается, потом зелёное.

## Разделение проверок

Граница проходит по имени файла и по команде, а не по пропуску внутри проверки.

| Набор | Файлы | Команда | Идёт в `ci` |
|---|---|---|---|
| Обычный | `__tests__/**/*.test.ts` | `npm test` | да |
| Живой | `__tests__/live/*.live.ts` | `npm run test:live` | нет |

Живые файлы названы `*.live.ts` и под образец `include` обычного набора не подходят вовсе.
Проверка не «пропускается при отсутствии ключей» — она просто не входит в этот набор; а будучи
запущенной без ключей, краснеет.

### Задача 1: путь к базе с явно названной средой

**Файлы:**
- Создать: `lib/ingest/target.ts`, `__tests__/ingest/target.test.ts`

Загрузчику нужна то локальная база, то боевая. Замок `lib/db-url.ts` писался для разрушающей
команды и разрешает единственную локальную базу — ослаблять его нельзя, поэтому у загрузчика
свой путь. Среда называется словом в переменной окружения; выводить её из косвенных признаков
запрещено.

**Интерфейсы:**
- Отдаёт наружу: `resolveIngestTarget(env?)` → `{ where: 'local' | 'production', url, label }`;
  `assertProductionDatabase(url)` → тот же адрес, если он годен, иначе ошибка.
- `label` — строка вида `цель: local, база nordic_pet на 127.0.0.1` без пароля.

- [ ] **Шаг 1: написать падающие проверки**

Создать `__tests__/ingest/target.test.ts`. Проверяется:

| Что | Ожидание |
|---|---|
| `NORDIC_PET_DB_TARGET` не задана | ошибка называет переменную и оба допустимых значения |
| значение `prod`, `LOCAL`, пустая строка | ошибка; молчаливого приведения нет |
| `local` | адрес совпадает с `projectDatabaseUrl()`, `where === 'local'` |
| `production`, а `SUPABASE_DB_URL` не задана | ошибка называет переменную |
| боевой адрес на `127.0.0.1` / `localhost` | отказ: «бой» не может указывать на локальный хост |
| боевой адрес с `sslmode=disable` | отказ |
| боевой адрес без порта / без имени базы / без пользователя / без пароля | отказ на каждую часть отдельно |
| годный боевой адрес | возвращён как есть, `where === 'production'` |
| **любое** сообщение об отказе | не содержит подстроки пароля из адреса |
| `label` боевой цели | содержит хост и имя базы, не содержит пароля |

Последние две — главные в этой задаче. Пример:

```ts
const секрет = 'сюда-нельзя-смотреть'
const адрес = `postgresql://ingester:${секрет}@db.example.supabase.co:6543/postgres?sslmode=require`

test('пароль не попадает в сообщение об отказе', () => {
  // адрес годен по всем частям, кроме отключённого шифрования
  const плохой = адрес.replace('sslmode=require', 'sslmode=disable')
  expect(() => assertProductionDatabase(плохой)).toThrowError(/sslmode/)
  try {
    assertProductionDatabase(плохой)
  } catch (e) {
    expect(String(e)).not.toContain(секрет)
  }
})
```

`npx vitest run __tests__/ingest/target.test.ts` — красное, потому что файла `lib/ingest/target.ts`

- [ ] **Шаг 3: написать `lib/ingest/target.ts`**

Требования к разбору боевого адреса: схема `postgresql:`/`postgres:`; хост назван и не входит в
список локальных; порт, имя базы, имя пользователя и пароль названы явно; `sslmode` не равен
`disable`. Адрес возвращается как есть — **не пересобирается**: пересборка потребовала бы
перекодировать пароль, а это ещё одно место, где написанное и понятое драйвером разойдутся.

Требование называть каждую часть закрывает то же, что закрывает пересборка в S1: драйвер `pg`
дочитывает недостающее из переменных `PG*`. Это проверено опытом, вывод — в теле pull request.

Список локальных хостов в этом файле свой, а не взятый из `lib/db-url.ts`: тот файл не меняется
ни на строку, включая список экспортируемого. Три адреса продублированы сознательно.

### Задача 4: загрузчик

**Файлы:**
- Создать: `lib/ingest/load-sheets.ts`, `__tests__/ingest/load-sheets.test.ts`

Здесь сходится всё: цель, чтение, разбор, запись. Это главная задача куска.

**Интерфейсы:**
- `ingestSheets(deps?)` → отчёт: цель загрузки; по каждому листу — прочитано, записано,
  пропущено пустых, лишние столбцы; по каждой таблице — количество строк и время последнего
  изменения.
- `deps` — источник листов, способ соединения с базой и `announce` для строки «куда пишем».
  У всех троих настоящие значения по умолчанию: вызов `ingestSheets()` без аргументов идёт
  настоящим путём.

**Порядок работы:** определить цель → объявить её через `announce` → прочитать все шесть листов →
построить шесть снимков → **только теперь** соединиться → `begin` → шесть вызовов
`raw.replace_*` → счётчики → `commit`. Любая ошибка разбора случается до соединения: до базы
дело не доходит вовсе.

- [ ] **Шаг 1: написать падающие проверки**

Проверки идут на живой локальной базе через подставленный источник листов. Все — внутри
транзакции с откатом, как в S1 (`inRollback` из `__tests__/db/support.ts`).

| Что | Ожидание |
|---|---|
| шесть листов | легли в шесть сырых таблиц, содержимое совпало посимвольно |
| соседние таблицы | `raw.ads` не тронута |
| одна транзакция | сбой на четвёртом листе не оставил в базе первых трёх |
| второй прогон того же снимка | **содержимое таблиц совпало целиком, включая `updated_at`** |
| исчезнувшая строка | во втором снимке строки нет — в таблице её тоже нет |
| ошибка разбора | до базы не дошло: соединение не открывалось |
| какие операторы посланы | только `begin`, `select raw.replace_*(…)`, чтение счётчиков, `commit` |

Идемпотентность доказывается сравнением содержимого, а не количеством строк: количество не
заметит переписанного содержимого и подскочившего `updated_at`.

Наблюдение за операторами — подставленное соединение, которое записывает каждый запрос и
передаёт его настоящему клиенту:

```ts
const посланные: string[] = []
const наблюдающий = (client: PoolClient) => ({
  query: (sql: string, params?: unknown[]) => { посланные.push(sql); return client.query(sql, params) },
})
// после загрузки:
expect(посланные.filter((s) => !/^(begin|commit|select raw\.replace_|select count)/i.test(s.trim())))
  .toEqual([])
```

Эта проверка — про поведение, а не про текст исходника, но она видит только тот путь, по
которому её прогнали. Настоящий замок — права роли в базе — отложен; см. раздел «Отложено».

## Отложено на потом — в тело pull request списком задач

- **Замок на разрушающие операторы.** Загрузчик ходит в базу полноправным пользователем.
  Настоящий замок — отдельная роль с правом на вызов шести функций `raw.replace_*` и чтение
  сырых таблиц, и ничего больше. Требует, чтобы функции S1 стали функциями с правами
  определяющего и жёстко заданным путём поиска, — это изменение модели безопасности базы и
  миграция в боевую базу, то есть свой кусок работы со своим разбором. До тех пор «загрузчик
  ничего не разрушает» — обещание кода, а не запрет базы.
- **Подготовленные запросы и пулер Supabase.** Режим транзакций (порт 6543), который Supabase
  рекомендует бессерверным клиентам, подготовленных запросов не поддерживает, а драйвер `pg`
  работает ими. В S2 не проявится — боевого соединения нет ни одного. Проявится при первом
  нажатии кнопки на S5: ошибка про подготовленный запрос, который «уже существует» или «не
  существует», со второго запроса в соединении. Средство — сменить `SUPABASE_DB_URL` на пулер
  в режиме сессии (порт 5432) или на прямое соединение; это одна переменная в Vercel и ни
  строки кода.

# S5 — семь правил счёта, экран и кнопка «Обновить данные». План работ

> **Для исполнителя:** план выполняется задача за задачей. Шаги отмечаются галочками (`- [ ]`).
> Каждая задача заканчивается коммитом и проверяемым результатом.

**Цель:** экран показывает за выбранный месяц выручку, затраты, итог, таблицу товаров и
честность данных; кнопка перечитывает оба источника; экран не считает ничего сам. Числа на
экране равны числам, которые выдают проверки, — потому что и экран, и проверка берут один и
тот же отчёт.

**Устройство:** весь счёт идёт в `numeric` Постгреса одним запросом на снимке фактов, взятом
в одной транзакции `repeatable read read only`. Слой метрик отдаёт готовые строки; страница
их печатает. Кнопка зовёт те же функции, что и команды S2, S3 и S4.

**Инструменты:** драйвер `pg`, vitest, PostgreSQL 15, Next.js 16 (серверные компоненты и
серверные действия). Новых зависимостей не появляется. Библиотека десятичной арифметики не
нужна и не заводится: деньги не становятся числом JavaScript ни разу.

**Контракт:** `.contracts/s5-metrics.md` на ветке `contract/s5-metrics` (коммит `e0f89ff`).
План спорит с контрактом, а не заменяет его: исполнитель читает оба.

## Общие ограничения

- **Ни одно денежное число не становится `number`.** Из базы `numeric` приходит строкой,
  строкой и уходит на экран. Арифметика — только в SQL. `parseFloat`, `Number()`, `+` над
  деньгами — стоп-сигнал, а не приём.
- **Округление одно и на выходе.** `round(x, 2)` в последнем выражении запроса, `round(x, 1)`
  для процентов. Промежуточных округлений нет нигде.
- **Процент комиссии делится на сто.** `fact.fees.percent` хранится в пунктах: `1.9000`,
  а не `0.0190`. Проверено на местной базе.
- **`coalesce(x, 0)` над деньгами разрешён ровно там, где это написано в контракте**, и каждое
  такое место обязано иметь строку в блоке неполноты. Новое место — это правка контракта, а не
  решение по дороге.
- **Дверь в базу принимает только `(sql: string, params?: unknown[])`.** Объект-запрос с полем
  `name` — именованный запрос, а объединитель соединений в режиме транзакций их не держит.
  Сверх типа стоит проверка времени выполнения: тип стирается при сборке.
- `lib/facts/**`, `lib/ingest/**`, `scripts/ingest-*.ts`, `scripts/build-facts.ts`,
  `lib/db-url.ts`, `supabase/migrations/**`, `supabase/seed.sql`, `vitest.config.ts`,
  `vitest.live.config.ts`, `.github/workflows/ci.yml` не меняются ни на строку. Задача,
  упирающаяся в необходимость их поправить, — стоп-сигнал, а не повод править.
- В схеме `fact` не появляется ни одной таблицы, ни одной колонки, ни одной миграции.
  Слой метрик только читает.
- Проверки пишутся до кода и сперва краснеют. Красное показывается, потом зелёное.
- Каждые ворота проверяются кодом возврата своей команды, а не конвейером.
- Экран в интернет не выкладывается. Деплой и вход по паролю — S6.

## Признак сохранения — обязателен в каждой задаче

Задачи этого плана выполняются разными исполнителями, и каждый приходит без памяти о том, что
уже принято. Поэтому признак сохранения проверяется **в каждой задаче**, а не один раз.

**Что обязано остаться зелёным без единой правки:**

1. Все проверки S1, S2, S3 и S4. Ни один их файл не открывается.
2. **Все проверки задач S5, законченных до текущей.** Задача N не открывает файлы проверок
   задач 1…N−1.
3. `npm run breaks -- s4-facts` возвращает ноль — **в тех задачах, которые тронули хоть один
   файл из перечисленных в `breaks/s4-facts.ts`** (сегодня это `lib/facts/*`, `lib/commands.ts`,
   `scripts/*` и миграция записи фактов), и обязательно в задачах 10 и 11. В остальных задачах
   признак сохранения — зелёный `npm test` целиком: он и так гоняет все проверки S4. Прибор
   правит файлы и гоняет набор на каждый из 85 сломов; двенадцать прогонов подряд стоят часы и
   ничего не добавляют там, где файлы S4 не тронуты. С задачи 10 добавляется
   `npm run breaks -- s5-metrics`.

**Правка принятой проверки ради зелени новой задачи — находка к владельцу, а не деталь по
дороге.** Даже когда правка выглядит очевидно верной, даже когда проверка выглядит неточной.
Исполнитель, которому мешает принятая проверка, останавливается и говорит об этом; он не
чинит её сам. Причина простая: принятая проверка сторожит утверждение, которое кто-то уже
доказал, и её правка снимает сторожа молча — а выглядит это как обычная строка в диффе.

Ровно один случай уже был: в S4 пришлось поправить проверку S1, и это делалось **с прямого
разрешения владельца**, а не по ходу работы.

**Как исполнитель это показывает.** В конце задачи, до коммита:

```bash
npm test > /tmp/task-N-tests.txt 2>&1; echo "npm test: $?"
npm run lint > /tmp/task-N-lint.txt 2>&1; echo "lint: $?"
npm run breaks -- s4-facts > /tmp/task-N-breaks.txt 2>&1; echo "breaks s4: $?"
git diff --name-only HEAD~1 HEAD
```

Коды возврата берутся у своих команд и никогда через конвейер: в оболочке код конвейера —
это код последней программы в нём, и `npm test | tail -5` вернёт успех хвостовика при
красных проверках.

Список изменённых файлов показывается целиком. Если в нём есть файл проверок прошлой задачи
или прошлого куска — задача не закончена, а остановлена, и об этом говорится вслух.

## Чем задача заканчивается

Отчёт исполнителя называет три вещи, и все три проверяемы со стороны:

| Что назвать | Зачем |
|---|---|
| Какой механизм задача добавила | чтобы было что ломать |
| Какая проверка этот механизм сторожит — **по имени** | «покраснело что-нибудь» ничего не доказывает |
| Коды возврата ворот, каждый от своей команды | «похоже, работает» — не результат |

Механизм без названной проверки считается недоказанным, даже если ворота зелёные. Задачу
принимают, сломав объявленный механизм и увидев красной именно названную проверку.

```ts
export type MetricsClient = {
  query: (sql: string, params?: unknown[]) => Promise<{ rows: Array<Record<string, unknown>> }>
  release: () => Promise<void>
}
export type MetricsDeps = {
  connect: (connection: string | ProductionConnection) => Promise<MetricsClient>
  announce: (line: string) => void
}
/** Открывает снимок фактов и отдаёт его функции. Транзакция всегда откатывается. */
export async function withFactSnapshot<T>(
  run: (client: MetricsClient) => Promise<T>,
  deps?: Partial<MetricsDeps>,
): Promise<T>
```

Цель — не общая обёртка на вырост, а три обязательства разом: цель названа до работы, снимок
один на весь экран, и записи в базу нет по устройству транзакции.

```ts
import { describe, expect, test } from 'vitest'
import { withFactSnapshot } from '@/lib/metrics/report'

describe('снимок фактов', () => {
  test('открывается на повторяемом чтении и только на чтение', async () => {
    const sent: string[] = []
    await withFactSnapshot(async () => 'готово', {
      announce: () => {},
      connect: async () => ({
        query: async (sql: string) => {
          sent.push(sql.trim().toLowerCase())
          return { rows: [] }
        },
        release: async () => {},
      }),
    })
    expect(sent[0]).toBe('begin isolation level repeatable read read only')
  })

  test('цель названа до первого запроса', async () => {
    const events: string[] = []
    await withFactSnapshot(async () => 'готово', {
      announce: (line) => events.push(`цель: ${line}`),
      connect: async () => {
        events.push('соединение')
        return { query: async () => ({ rows: [] }), release: async () => {} }
      },
    })
    expect(events[0]).toMatch(/^цель: /)
    expect(events).toContain('соединение')
    expect(events.indexOf('соединение')).toBeGreaterThan(0)
  })

      withFactSnapshot(

            name: 'totals',
            text: 'select 1',
          }),
        {
          announce: () => {},
          connect: async () => ({ query: async () => ({ rows: [] }), release: async () => {} }),
        },
      ),
    ).rejects.toThrow(/именованный запрос/)
  })

  test('соединение отпускается даже когда работа отказала', async () => {
    let released = false
    await expect(
      withFactSnapshot(async () => { throw new Error('нарочно') }, {
        announce: () => {},
        connect: async () => ({
          query: async () => ({ rows: [] }),
          release: async () => { released = true },
        }),
      }),
    ).rejects.toThrow('нарочно')
    expect(released).toBe(true)
  })

  test('на настоящей базе без единого довода: запись внутри снимка невозможна', async () => {
    process.env.NORDIC_PET_DB_TARGET = 'local'
    const code = await withFactSnapshot(async (client) => {
      try {
        await client.query('create temporary table проба (x int)')
        return 'записалось'
      } catch (error) {
        return (error as { code?: string }).code ?? 'без кода'
      }
    })
    expect(code).toBe('25006')
  })
})
```

**Разрешение на вынос.** Задача 3 вправе перенести подставку из `__tests__/metrics/revenue.test.ts`

Проверяется это диффом, а не обещанием. Любая другая правка принятой проверки — находка к
владельцу, а не деталь по дороге.

```ts
type OrderRow  = { order: string; sku: string; date: string; units: number
                   gross: string | null; discount: string | null; gateway: string }
type RefundRow = { order: string; sku: string; date: string; units: number; amount: string | null }
type CostRow   = { sku: string; cost: string | null; from: string }
type Extras = {
  fees?: Array<{ gateway: string; percent: string; fixed: string }>
  opex?: Array<{ month: string; category: string; amount: string | null }>
  ads?: Array<{ file: string; row: number; date: string; campaign: string
                platform: string; spend: string | null }>
  fx?: Array<{ date: string; rate: string }>
}

/**
 * Кладёт выдуманные факты в откатываемую транзакцию и возвращает строку итогов месяца.
 * Умолчания: одна ставка `card` 1.9000 + 0.25, ни расходов, ни рекламы, ни курса —
 * чтобы проверка выручки не зависела от того, чего она не проверяет.
 */
async function totalsOn(
  orders: OrderRow[],
  refunds: RefundRow[],
  month: string,
  costs: CostRow[] = [],
  extras: Extras = {},
): Promise<Record<string, string | null>>
```

```ts
test('чистая выручка = оборот − скидки − возвраты', async () => {
  const totals = await totalsOn([
    { order: 'A-1', sku: 'NP-001', date: '2026-03-02', units: 2, gross: '100.00', discount: '10.00', gateway: 'card' },
  ], [
    { order: 'A-1', sku: 'NP-001', date: '2026-03-05', units: 1, amount: '30.00' },
  ], '2026-03')
  expect(totals.gross).toBe('100.00')
  expect(totals.discounts).toBe('10.00')
  expect(totals.refunds).toBe('30.00')
  expect(totals.net).toBe('60.00')

  const далеко = await totalsOn(orders, [{ order: 'A-1', sku: 'NP-001', date: '2026-04-30', units: 1, amount: '40.00' }], '2026-03')
  // Сравнение двух итогов друг с другом зелено и на сплошных нулях; число закрепляется отдельно.
```

```sql
with bounds as (
  select $1::date as first_day, ($1::date + interval '1 month')::date as next_month
),
order_day as (
  select o.order_id, min(o.date) as sold_on
    from fact.orders o
   group by o.order_id
),
lines as (
  select o.order_id, o.sku,
         min(d.sold_on)               as sold_on,
         min(o.gateway)               as gateway,
         sum(o.units)                 as units,
         sum(o.gross)                 as gross,
         sum(coalesce(o.discount, 0)) as discount
    from fact.orders o
    join order_day d on d.order_id = o.order_id
    cross join bounds b
   where d.sold_on >= b.first_day and d.sold_on < b.next_month
     and o.gross is not null
   group by o.order_id, o.sku
),
returned as (
  select r.order_id, r.sku,
         sum(r.amount)             as amount,
         coalesce(sum(r.units), 0) as units
    from fact.refunds r
   group by r.order_id, r.sku
),
counted as (
  select l.order_id, l.sku, l.sold_on, l.gateway, l.units, l.gross, l.discount,
         coalesce(t.amount, 0) as refund_amount,
         coalesce(t.units, 0)  as refund_units
    from lines l
    left join returned t on t.order_id = l.order_id and t.sku = l.sku
),
money as (
  select c.*, c.gross - c.discount - c.refund_amount as net from counted c
),
totals as (
  select sum(gross) as gross, sum(discount) as discounts,
         sum(refund_amount) as refunds, sum(net) as net
    from money
)
select round(coalesce(gross, 0), 2)::text     as gross,
       round(coalesce(discounts, 0), 2)::text as discounts,
       round(coalesce(refunds, 0), 2)::text   as refunds,
       round(coalesce(net, 0), 2)::text       as net
  from totals
```

Три вещи, из-за которых запрос выглядит именно так. Возвраты соединяются по паре
«заказ + артикул» и **не фильтруются по своей дате** — в этом всё правило 2.

Месяц берётся у **заказа целиком**, через `order_day`, а не у отдельной строки. Заказ
принадлежит одному дню — это обязательство S4, — но слой метрик не опирается на чужой отказ,
а исполняет то же сам. Без этого заказ, чьи строки разошлись датой, получил бы свой возврат
дважды: свёртка `returned` идёт по паре и месяца не знает. Проверка кода доказала это
запуском — 100,00 марта и 100,00 апреля по одной паре с возвратом 40,00 давали чистую
выручку 60,00 в обоих месяцах.

И `o.gross is not null` стоит в `lines`, то есть отсеивает **строку источника**, а не
свёрнутую пару. Первая редакция этого плана ставила условие после свёртки, и слом нашёл
там дефект. Пара с одной пустой и одной заполненной строкой переживает отсев по свёртке —
`sum(gross)` пропускает пустые, — и приносит в счёт скидку той строки, выручки которой мы не
знаем. Проверено запуском на настоящей базе: отсев по свёртке даёт оборот 10,00 при скидках
5,00, отсев по строке — оборот 10,00 при скидках 0,00. Вычет неизвестного происхождения —
то же враньё, что ноль вместо пустой ячейки, только пришедшее с другой стороны.

Условия в `counted` при этом нет вовсе: после отсева по строке пара без единой суммы просто
не существует, и повторное условие было бы недостижимым замком.

```sql
    from fact.opex x, bounds b
```

`spend / usd_per_eur` — деление, а не умножение: `usd_per_eur` это доллары за евро.
`fe.percent / 100` — то самое деление на сто. `sum(gross - discount)` берётся из `lines`, то
есть **до** вычета возвратов: допущение 3 владельца. Условия `gross is not null` здесь нет:
строки без суммы отсеяны в `lines` ещё в задаче 2.

Три вещи в этом фрагменте появились после того, как проверка кода нашла в первой редакции
плана два критичных места. Читать их стоит вместе с контрактом.

**Части ставки складываются раздельными слагаемыми.** Записанная одной формулой,
`amount * percent/100 + fixed` при пустом проценте даёт `NULL` на весь заказ; суммирование
пропускает его, `coalesce` превращает в ноль, и комиссия **всего способа оплаты** обращается
в ноль. Для марта это 0,00 € вместо 526,12 €. Проверено запуском. Раздельные слагаемые уносят
только неизвестную часть.

**`nullif(f.usd_per_eur, 0)`.** Нулевой курс иначе рвёт запрос делением на ноль и гасит весь
экран — против решения владельца 4. Пустой курс до фактов доезжает: отказ S4 сверяет наличие
строки на дату, а не её значение. «Нет курса», «курс пуст» и «курс ноль» — одно понятие.

**`count(distinct gateway)` и условие `gateways = 1`.** `min(gateway)` молча применял бы
ставку алфавитно первого способа ко всей сумме заказа: проверка кода получила так 2,25 €
вместо 25,00 €. Опираться здесь на отказ S4 было бы непоследовательно — в задаче 2 мы от
такой опоры отказались.

**Двух холостых условий больше нет.** `a.spend is not null` и `x.amount is not null` числу не
давали ничего: суммирование пропускает пустые само. Недостижимое условие создаёт видимость
замка, которого нет.

## Список сломов

Список живёт данными в `breaks/s5-metrics.ts` и прогоняется командой
`npm run breaks -- s5-metrics`. Таблица в теле pull request **порождается выводом прогона**,
а не набирается руками: иначе «каждый слом покраснел» снова станет утверждением автора.

Строк — **75**, и они перечислены таблицей в контракте, раздел «Что ломаем — что обязано
покраснеть». Здесь только разбивка по файлам проверок, чтобы исполнитель видел, куда какой
слом целится, и распределение по задачам.

| Куда целятся сломы | Сколько | Появляются в задаче |
|---|---|---|
| правила счёта: выручка, возвраты, привязка к месяцу заказа | 10 | 2 |
| правила счёта: себестоимость, цена на дату, запасные проценты | 11 | 3 |
| правила счёта: реклама, курс, комиссия, пункты против доли | 16 | 4 |
| итог, маржа, окупаемость, доля честности, нет данных вместо нуля | 11 | 5 |
| блок неполноты и адреса дыр | 10 | 5 |
| снимок фактов, транзакция, именованные запросы | 4 | 1 |
| экран: печатает отчёт, не считает, подписи словами | 4 | 7 |
| кнопка, щель, порядок шагов, шаги из списка, стук наружу | 8 | 8 |

**Три правила про сломы, из-за нарушения которых в S4 было потеряно три круга.**

1. `mustRedden` обязан подходить **ровно к одной** проверке набора. Имя, подходящее к
   семейству, засчитывает красное у соседки вместо красного у своей.
2. Покрасневшее сверх объявленного — отказ прибора, а не мелочь. Либо слом сужается, либо
   лишнее объявляется в `alsoRedden` **с причиной у каждой строки**.
3. Слом обязан отрицать именно то, что написано в его строке. Утверждение про порядок
   («цель названа до работы») отрицается переносом, а не удалением: удаление краснит что
   угодно и не доказывает ничего.

Известное ограничение, унаследованное от S4 и не устраняемое здесь: прибор заморожен по
правилу владельца о третьем круге. Имя побочной проверки не проверяется на точность, объявить
побочным лишнее ничего не стоит, сам прибор сломами не покрыт. Вердикт «75 из 75» будет
значить ровно то же, что «85 из 85» в S4, — не больше, и в теле pull request это пишется

## Ловушки, которые уже известны

Записаны здесь, чтобы исполнитель узнал их по признаку, а не искал заново.

| Ловушка | По какому признаку узнать | Что делать |
|---|---|---|
| Процент как доля, а не пункты | комиссии выходят около 5 € вместо 526 € | делить на сто; ставка в базе — `1.9000` |
| Умножение на курс вместо деления | реклама около 5200 € вместо 4431 € | `spend / usd_per_eur` |
| Части ставки сложены одной формулой | пустой процент обнуляет комиссию всего способа оплаты: 0 € вместо 526 € | `sum(amount × percent/100)` и `sum(fixed)` раздельно |
| Нулевой курс без `nullif` | весь экран гаснет ошибкой деления на ноль | `nullif(usd_per_eur, 0)` |
| Правило 5 применено дважды | себестоимость около 5894 € вместо 6028 €, прибыль около 1872 € вместо 1739 € | ветка `else` берёт `net` один раз |
| Возврат больше купленного | себестоимость строки отрицательная; на настоящих данных не видно — таких строк ноль | `greatest(units − refund_units, 0)` |
| `coalesce(x, 0)` вместо `nullif` в знаменателе | на экране `0,0 %` или `NaN` вместо «нет данных» | `nullif(знаменатель, 0)` |
| Возврат отфильтрован по своей дате | чистая выручка около 17 550 € вместо 17 277 € | возвраты соединяются по паре, а не по дате |
| Месяц взят у строки, а не у заказа | на настоящих данных не видно; заказ с двумя датами получает возврат дважды | месяц берётся из `order_day` |
| Деньги прошли через `Number` | итог отличается на копейки, порог 0,5% при этом держится | искать `parseFloat`, `Number(`, `+` над строками денег |
| Именованный запрос на боевом пути | ошибка драйвера про подготовленный запрос на порту 6543 | искать поле `name` в объекте запроса |
| Отсев строк без суммы поставлен после свёртки пары | на смешанной паре скидка строки без суммы уменьшает выручку; на однородных данных незаметно | условие стоит в `lines`, по строке источника |

## Чего в этом плане нет

Входа по логину и паролю, закрытия адресов, публикации экрана в интернет, обновления по
расписанию, показа строк-близнецов на экране, нескольких магазинов и валют, красоты.

Отдельно: **пометка «числа могли устареть» появляется от неудачного нажатия кнопки и не
появляется при обычном открытии страницы.** Отличить «факты отстали от сырья» на холодном
открытии нечем — у таблиц фактов нет отметки времени, а восьмую таблицу в схеме `fact`
запрещает проверка S1. Это ограничение названо в контракте и уходит задачей в тело pull
request, а не чинится здесь молча.
